The pitch

Palimpsest watches the world's public knowledge being rewritten in real time and remembers every version as a directed, attributed property graph. A single edit is never suspicious; a coordinated campaign is — and Palimpsest catches the fourth move of a ring in one 3-hop Cypher query, in under five milliseconds, across entities that arrived at different times from different sources. Four specialist agents split the work, refuse to act without a human, and fire a real action with the full provenance chain attached. Then we prove the memory is load-bearing instead of claiming it: one keypress replays the identical event log from offset zero into an empty graph, and you watch the same agents, same model, same prompt, confidently make the wrong call. Kill the analyst mid-investigation and it restarts cold, reads its own handover node out of the graph, resumes from its committed stream offset, and finishes the case. Memory, visibly producing motion.

Canonical UX — the north star operator ruling

Every AI agent wakes up stateless and amnesiac. Not with ours. When you ask a question, the agent already knows who you are, who it is, and what is happening right now — it pulls the required context automatically instead of asking you for it. Conversations that used to be a multi-turn interrogation resolve in a single turn.

Every mechanic in this build exists to serve that sentence. The cold-vs-warm ablation IS this UX made visible: the amnesiac agent hedges or interrogates; the informed agent answers in one turn.

Full component walk-through (9 components)

ONE LAPTOP, SIX PROCESSES, ONE LOG SPINE, ONE DISPATCH TABLE. Everything on the critical path is localhost; only Guild's control plane needs the network.

[1] EDGE TAP — realtime/producer.py (~25 LOC). Holds an httpx SSE stream on Wikimedia EventStreams (https://stream.wikimedia.org/v2/stream/recentchange — zero-auth, verified live, 50-100 ev/s) and publishes every edit to LaserData topic `signal.raw` with key=wiki so per-wiki ordering survives parallel consumers. 4 partitions, batch_length=200, linger_ms=50, producer.init() BEFORE first send. A `--source file://demo/seed_replay.ndjson` flag drives the SAME code path from a 20-minute captured firehose, so conference wifi is never on the critical path. This is the only process that touches the public internet for ingest.

[2] LASERDATA PLANE — local laser-stack (iggy-server + laser-plane via Docker). Six topics: signal.raw, signal.salient, case.opened, case.decision, action.executed, agent.handoff. LaserData is the ONLY interface between services: every memory write, every RocketRide tool call, every Guild handoff, and every human ruling is a durable ordered record. Consumer group `graph-writers` with N members; the server assigns one partition per member and rebalances live on join/kill. auto_commit=disabled, commit-AFTER-side-effects-land. HARD SCOPE RULE: Log primitive ONLY. Views/Changes/State/Graph/Memory are never called, and every capability beyond Log is gated behind `await laser.capabilities()` — which is exactly what makes local-stack -> LaserData Cloud -> bare Apache Iggy a one-env-var swap.

[3] SENSING GATE — realtime/gate.py, between consumer and graph. Embeds the candidate edit summary, runs a FalkorDB vector KNN, drops the write if top-1 cosine DISTANCE is under threshold (0.15, ported from unblock's sensing-gate). Without it a 50-100 ev/s firehose turns the projector graph into an unreadable hairball in four minutes — and the visual IS the pitch. Judge-visible stat: "41,208 events ingested, 912 nodes — the gate rejected 97% as non-novel."

[4] MEMORY — FalkorDB, memory/. falkordblite EMBEDDED, forced onto TCP via serverconfig={'port':'6401','bind':'127.0.0.1'}. Port 6401, NOT 6379 and NOT 6399 — verified in-session today that a stray redis-server already holds 6399 on the build Mac, and a 6379 collision produces a false-green (client connects fine, then fails on GRAPH.QUERY). Zero Docker, zero daemon, zero network: this is the least-breakable layer in the stack, which is why it is the local-of-record.
Two graph keys on one server: `palimpsest` (warm, the real memory) and `palimpsest_cold` (empty, the A/B target).
Nodes: :Actor, :Page, :Wiki, :Event, :Entity, :Claim, :Case, :Agent, :Assertion, :Action.
Edges: [:EDITED {ts,bytes,summary}], [:ON], derived [:CO_EDITED_WITH {window_s,count}], [:ABOUT], [:MENTIONS], [:IMPLICATES], [:AUTHORED], [:RELATES {relation}] over unblock's 6-value vocabulary (supports|contradicts|derived_from|supersedes|duplicates|references) stored GENUINELY DIRECTED, and [:HANDED_OFF_TO {handover_id,status,summary,in_flight,next_steps,blockers,checkpoint}].
Indexes: range on Actor.name, Page.title, Case.id; HNSW vector on Claim.emb and Event.emb (dim 256, cosine) for hybrid GraphRAG entry.
memory/graph_writer.py (consumer group graph-writers) does gate -> Cypher MERGE -> emit delta to the UI topic. NO LLM ON THE LIVE PATH — milliseconds, and nothing to hang on stage. GraphRAG-SDK is pre-bake ONLY (batch, finalize() exactly once, it is O(total graph size)).

[5] THE SPINE / BRIDGE — app/bridge/, FastAPI, built on unblock's 4-tuple _VERB_DISPATCH table with the ~35-LOC generic router. ONE table, FOUR surfaces, and this is the single decision that makes the sprint finishable:
(a) REST — consumed by the UI and the seed script
(b) MCP streamable-http — mounted into RocketRide via its mcp_client node
(c) auto-generated OpenAPI 3.0 spec — becomes the ONE Guild Integration (Guild's sandbox bans fetch/npm/Node built-ins, so an Integration is the only legal door; three of them would eat the sprint)
(d) CLI — rehearsal + gate-artifact capture
Verbs: remember, relate, recall, ring, graph, stream_publish, stream_tail, stream_replay, act, handover_write, handover_read, ask. Every verb flows through ONE request chokepoint so retries, error envelopes, and headers live in one place.

[6] MOTION — RocketRide, motion/palimpsest.pipe. Engine ALREADY BOOTED on this box (PID 9858, 127.0.0.1:5565, dev key MYAPIKEY, MIT, self-hosted, no signup). Graph: webhook_1 -> question_1 -> agent_rocketride "Commander" (Wave planner, max_waves=12) with control-attached llm_anthropic (Claude Sonnet), memory_internal, tool_falkordb (host 127.0.0.1, port 6401, graph=palimpsest, allow_writes=true — a FIRST-PARTY FalkorDB node, so the agent itself chooses to call falkordb.get_schema then falkordb.query), tool_http_request (Discord webhook + GitHub API), mcp_client (our bridge), and a researcher sub-agent with its own llm_anthropic (Haiku) + memory_internal -> response_answers. Driven with ttl=0, pipelineTraceLevel="full", set_events(token,[task,summary,flow,output,sse]) so `thinking` frames stream into the UI as live narration. Our Python is ~40 lines; the orchestration is ~130 lines of .pipe JSON.

[7] COORDINATION — Guild.ai, agents/. Four published agents: watcher (LaserData ops on the bridge integration), analyst (FalkorDB ring/recall + claim extraction), responder (fires the action via /act -> RocketRide), and commander which imports the other three as auto-generated typed /tool sub-packages — that import IS the handoff, with Zod schemas inherited from the callee. commander runs task.gather([watcher, analyst]) for genuine parallel NOW-parallel-EVER, then ui_prompt BLOCKS for human approval (options + recommendation + timeoutSec + DEFAULT-ON-TIMEOUT, shape lifted from unblock's AskOpts), then delegates to responder. useWorkspaceAgents:false set EXPLICITLY (it defaults true, which makes coordination look accidental to a judge).

[8] IDENTITY — session_persona.py ported near-verbatim: one bridge process serves N distinct agent identities keyed on Mcp-Session-Id / per-request header, zero cross-bleed. Every Cypher write is stamped author_agent. This is what makes "agent A contradicted agent B" a graph fact rather than a caption.

[9] PROJECTOR UI — app/web/index.html. Single file, no build step, dark, projector-sized type. Four regions: LIVE GRAPH (force-directed canvas, nodes/edges streamed off the log, animated path highlight when the analyst traverses), AGENT LANE (Guild handoffs + RocketRide SSE thinking), CASE/ACTION panel (fired actions with clickable URLs), and the LaserData offset/lag strip. Plus a COLD | WARM split toggle for the replay A/B. The UI holds NO state — it is a pure projection of the log and the graph.

DATA FLOW (the mandated flow, executing literally): human edits a wiki page -> SSE -> LaserData signal.raw -> consumer group -> sensing gate -> FalkorDB MERGE (+ delta to UI) -> ring Cypher -> if ring_score > threshold, publish case.opened + POST the Guild trigger -> commander task.gather(watcher || analyst) -> analyst's 3-hop Cypher joins the live edit to the pre-baked historical corpus -> RocketRide Wave agent calls falkordb.get_schema + falkordb.query + tool_http_request in ONE parallel wave and decides escalate/dismiss -> ui_prompt -> human approves -> responder fires Discord + a GitHub issue -> the action is written BACK as (:Action)-[:RELATES {relation:'derived_from'}]->(:Event) so every action has clickable provenance -> UI renders. Every one of those arrows is a durable LaserData record.

Sponsor integration — load-bearing proofs & removal tests

Judging criterion is "load-bearing use of all four technologies." Every card ends in a removal test; fallback ladders are pre-agreed so nobody improvises at hour 6.

FalkorDB EVER — memory

ROLE: memory of record — and the layer that answers the question nothing else in the stack can express.

THREE LOAD-BEARING PROOFS, each with a removal test:
(1) THE RING QUERY. The escalate/dismiss verdict is computed from a single variable-length Cypher over a time window returning Path objects: MATCH p=(a:Actor)-[:EDITED]->(:Page)<-[:EDITED]-(b:Actor)-[:EDITED]->(:Page)<-[:EDITED]-(c:Actor) with ts-window and DISTINCT-actor constraints. Three accounts, four pages, twelve minutes — no individual edit crosses any threshold. We put run_time_ms (measured 2.45ms for 3 hops on this box) on screen next to the result. A vector store cannot express 'semantically similar to a four-step causal chain'.
(2) SUPERSEDE LINEAGE. MATCH p=(old:Claim{id:$id})<-[:RELATES*{relation:'supersedes'}]-(newest) WHERE NOT (newest)<-[:RELATES{relation:'supersedes'}]-() RETURN newest, length(p) — 'you told me X, then Y; here is the CURRENT truth and the chain that got there.' We also fix a real defect we inherited: unblock's contradiction_edges table has a block_id_a < block_id_b CHECK that forces DIRECTED relations to be stored UNDIRECTED (its own source comments flag it). We drop it, and say so: 'we improved on the production system we ported from.'
(3) HYBRID GraphRAG IN ONE QUERY. CALL db.idx.vector.queryNodes('Claim','emb',10,vecf32($q)) YIELD node AS seed MATCH (seed)-[:MENTIONS]->(e:Entity)<-[:MENTIONS]-(neighbor) — semantic entry, symbolic expansion, one round trip.

THE KILLER PROOF IS THE ABLATION, NOT THE CLAIM: identical event replayed twice from the same log, once into palimpsest and once into empty palimpsest_cold. Same model, same prompt, same agents. COLD -> 'Routine edit. No action.' WARM -> 'Coordinated campaign, 4th move. Escalate.' Both terminal outputs captured side by side as a saved gate artifact.

SECOND ROLE JUDGES DO NOT EXPECT: the agents' OWN continuity lives here. Findings, provenance, and the [:HANDED_OFF_TO {status:'open'}] handover nodes that make kill-and-resume work. So deleting FalkorDB also kills the demo's headline moment.

REMOVAL TEST: delete FalkorDB and there is no ring detection, no lineage, no attribution, no cold-resume, and the agent's decision measurably degrades on camera.

BOUNDARY WE STATE OUT LOUD: LaserData's SDK ships laser.graph() and laser.memory(). We deliberately do not call them. Laser is NOW plus the spine; FalkorDB is EVER.

LaserData NOW — spine

ROLE: the nervous system — and we make it the ONLY interface between services, so it is architecture rather than an import, and unfalsifiable to a judge.

HONEST FRAMING WE SAY UNPROMPTED, BEFORE ANYONE ASKS: LaserData does not supply data, it moves it. We bring the source (Wikimedia's zero-auth public firehose); LaserData carries, orders, durably stores, partitions, and replays it. Saying that out loud reads as rigor, not weakness.

FOUR LOAD-BEARING PROOFS:
(1) REPLAY AS THE PROOF ITSELF — our single strongest beat. The cold-vs-warm A/B is IMPLEMENTED as a durable replay: a fresh consumer at polling='first' from offset 0 re-derives the entire graph from scratch into the empty palimpsest_cold key in seconds. 'Watch me rewind and re-derive the memory' is the literal embodiment of memory meets motion, and no other sponsor in the stack can do it. One mechanic, two sponsors, zero hand-waving. We also assert node/edge digests match the live-built graph.
(2) CONSUMER GROUPS AS THE AGENT SUBSTRATE. graph-writers has N members; the server assigns one partition per member and rebalances live. We kill a member on stage and show partitions redistribute with zero coordinator and zero message loss (committed offsets asserted before and after). key=wiki preserves per-entity ordering across the whole team.
(3) CRASH-SAFETY IS THE DEMO. auto_commit=disabled with commit-after-side-effects means the kill-and-resume beat resumes from the exact committed offset. Delete LaserData and cold-restart loses its 'motion' half — FalkorDB only restores the 'memory' half. Both mandated layers are structurally required for the headline trick.
(4) EVERY ACTION IS A RECORD. Memory writes, RocketRide tool calls, Guild handoffs, and human rulings all publish to the six topics. 'Every tool call this system ever made is on the log and I can replay any of them' is true, not aspirational.

CORRECTNESS: our consumer ports unblock's four hard-won streaming invariants verbatim (enqueue-before-ack, dedup on stream sequence NOT message_id, backpressure-not-drop, cancellation-safe teardown). Delivery is at-least-once by design, so every graph write is a MERGE and every action record is keyed by case_id + decision_hash.

SCOPE DISCIPLINE: Log primitive only. Views/Changes/State/Graph/Memory are never called; everything beyond Log is gated behind await laser.capabilities(). That is what makes the fallback ladder a one-env-var swap rather than a rewrite — and it keeps laser.graph()/laser.memory() from cannibalizing FalkorDB's mandated role.

REMOVAL TEST: two commands. Stop the plane and all six processes stop exchanging; there is no replay, no crash recovery, no audit trail. The system does not start.

Judge Q&A prep

Is FalkorDB actually load-bearing, or is it a key-value store in a graph costume?

Run the ablation in front of you — it takes eight seconds. Identical event, replayed from the same log into two graph keys: warm returns 'coordinated campaign, escalate,' cold returns 'routine edit, dismiss.' Same model, same prompt, same agents. The verdict is computed from a variable-length Cypher co-edit traversal — (a:Actor)-[:EDITED]->(:Page)<-[:EDITED]-(b)-[:EDITED]->(:Page)<-[:EDITED]-(c) — returning Path objects in 2.45ms. Delete FalkorDB and there is no ring detection, no supersede lineage, no attribution, and no cold-resume, because the agents' own handover state lives in the graph too. We also improved on the production system we ported the model from: unblock's edge table has a block_id_a < block_id_b CHECK that forces directed relations to be stored undirected. We dropped it; ours are genuinely directed.

Why not just a vector database, or Postgres with a recursive CTE?

Two questions we answer that neither can express. First, the ring: 'semantically similar to a four-step causal chain across distinct actors within a twelve-minute window' is not a vector operation — there is no embedding of a path. Second, supersede-lineage: MATCH p=(old)<-[:RELATES*{relation:'supersedes'}]-(newest) WHERE NOT (newest)<-[:RELATES{relation:'supersedes'}]-() resolves current truth from a revision chain of unknown depth in one shot. A CTE can do the second with real effort; neither does the third thing, which is our hybrid GraphRAG query — db.idx.vector.queryNodes for semantic entry, then symbolic expansion through shared :Entity nodes, in ONE round trip. We use the vector index; we just do not stop there.

What did LaserData actually give you? You brought your own data.

We say this before you ask: LaserData does not supply data, it moves it. We bring Wikimedia's public firehose; LaserData carries, orders, partitions, durably stores, and replays it. And it is the ONLY interface between our six services — every memory write, every tool call, every handoff, every human ruling is a log record. Two commands falsify it: stop the plane and nothing exchanges. But the real proof is that our strongest beat IS a LaserData primitive — the cold-vs-warm A/B is implemented as a durable replay from offset 0, and only an ordered durable log lets you feed the exact same reality to two different agents. We also kill a consumer-group member on stage and show partitions rebalance with zero coordinator and zero message loss, with committed offsets asserted before and after.

Isn't Guild just four imports? Couldn't you do this with a Python script?

Read the trace, don't take my word: guild session events <id> is a server-side record showing commander -> analyst -> ui_prompt -> responder with per-agent identities, tool calls, token counts, and credential scopes. Three structural things a script does not give you. One: delegation is TYPED and runtime-dispatched — the /tool sub-package is generated at publish time and the caller inherits the callee's Zod schemas. Two: task.gather is branded to tool-call expressions only, so the parallel now-and-ever fan-out is genuinely Guild's runtime, not Promise.all. Three: the sandbox bans fetch, npm, and Node built-ins, so every external system reaches our agents only through a Guild Integration with server-side credential injection — agent code never sees a raw key. Agents are independent security principals. That is the answer to 'why not a script.'

Did you write the orchestration yourself and just call RocketRide once to summarize?

The exact opposite, and the file counts prove it: the orchestration is ~130 lines of motion/palimpsest.pipe JSON; our Python is ~40 lines of client — connect, use, send, stream. The agent loop, tool selection, retries, parallel fan-out, and sub-agent delegation all live in their engine. Delete the .pipe and NOTHING in our repo selects a tool. And watch the trace: the agent chose to call falkordb.get_schema to learn our memory model, then composed parameterized Cypher itself, through RocketRide's own first-party tool_falkordb node. That is a vendor-built integration, not glue we invented.

Show me the parallel execution you keep claiming.

Here — pipelineTraceLevel='full' with set_events([task,summary,flow,output,sse]). This is one Wave from the agent_rocketride planner containing two tool calls dispatched in the same batch: the live fetch and the graph recall, then the decision. That is the hackathon's reference flow — what's happening now plus what ever happened, then decide — executing as engine primitives rather than as our for-loop.

What is actually novel here versus a RAG chatbot?

Three things. One: the decision is a function of a TRAVERSAL, not a retrieval — and we prove it by ablation rather than claiming it. Two: every fact is attributed to the agent that asserted it, so contradictions between agents are directed edges in the graph, not prose, and a human breaks the tie before anything fires. Three: continuity survives the process. Kill the agent and it resumes from a handover node plus a committed stream offset — memory restoring what it knew, the log restoring where it was. A RAG chatbot has none of those; it re-retrieves and starts over.

What if the conference wifi dies right now?

Nothing on the critical path needs it. falkordblite is embedded on 127.0.0.1:6401 — no Docker, no daemon; laser-stack is local; the RocketRide engine is local and MIT-licensed with a built-in dev key. Only Guild's control plane is remote, and we drilled that segment against tape. Every service takes --offline and replays a captured 20-minute firehose through the identical code path, so the file source and the live source are literally the same code. We rehearsed the whole 90 seconds with wifi physically off.

How do I know any of this is real and not mocked?

Four handles, all live on that spare desktop. mcp_smoke.py calls a bridge tool in front of you right now. guild session events is a server-side trace whose rendering we do not control. The GitHub issue we just filed is a public URL — open it on your phone. And the Wikimedia firehose is zero-auth: curl https://stream.wikimedia.org/v2/stream/recentchange from your own laptop and watch the same events we're consuming.

Your stack has overlapping capabilities — LaserData ships its own graph and memory primitives. Which layer is really the memory?

We noticed that too, and we deliberately do not call laser.graph() or laser.memory(). Hard rule, stated in the README: LaserData owns 'what is happening now' plus the message spine; FalkorDB owns 'what ever happened.' Using both would muddy both sponsor stories and make it fair to ask you which one is decorative. We also use ONLY LaserData's Log primitive and gate everything else behind await laser.capabilities() — which is why the same code runs unchanged on local stack, their Cloud, or bare Apache Iggy.

Which model built the graph, and what happens when it's slow or rate-limited?

Claude, via LiteLLM in GraphRAG-SDK, for the pre-baked historical corpus — and here's the ontology it invented for itself from the raw documents. But there is ZERO LLM on the live path: streaming ingest is raw parameterized Cypher MERGE, milliseconds, nothing to hang. The LLM only runs inside the RocketRide decision loop with capped waves. We made that split deliberately, because GraphRAG ingest is an LLM call per chunk and finalize() is O(total graph size) — calling it in a streaming loop gets quadratically slower on stage.

How do you keep a 50-100 event/second firehose from turning the graph into noise?

A salience gate ported from a production system, running BEFORE every write: embed the candidate, run a vector KNN against the graph, and skip the MERGE if the nearest neighbour is closer than 0.15. That number on screen — 41,208 events in, 912 nodes kept — is the gate rejecting 97% as non-novel. Without it the ring query drowns in near-duplicates in about four minutes, and we found that out at hour 1, not on stage.

What would you do with another day?

Three things, in order. Narrow the ring detector from co-edit topology to timing-correlation scoring so it generalizes past Wikipedia. Make the contradiction resolution learn from human rulings — right now the ruling lands as a supersedes edge but nothing tunes the threshold from it. And harden attestation: we deliberately ship NO trust badge today, because the system we ported patterns from has attestation flags that are false in production with a live forgery path, and we would rather show you nothing than show you a hardcoded green checkmark.
